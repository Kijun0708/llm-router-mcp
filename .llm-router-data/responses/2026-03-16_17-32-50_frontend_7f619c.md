## Gemini Frontend 응답 (1분 4초)

## Current State Assessment

현재 대시보드의 UI 구조는 1~2명의 개발자가 CLI 환경에서 실행되는 다중 LLM 라우팅을 모니터링한다는 목적에 **매우 적합(Industrial/Utilitarian)**합니다. 장식적인 요소를 배제하고 시스템의 상태(Health, Rate Limit, Active Calls)를 즉각적으로 파악할 수 있는 기능주의적 접근이 돋보입니다. 

**What works:**
- **Global Health Bar**: 동시성과 큐 상태를 한 줄로 압축한 것은 훌륭한 밀도 조절입니다. 개발자는 색상과 게이지만으로 시스템 부하를 즉각 인지할 수 있습니다.
- **FLAT/TREE 토글**: 디버깅 시나리오에 따라 시간순 로그(FLAT)와 논리적 흐름(TREE)을 전환할 수 있게 한 점은 개발자의 멘탈 모델을 정확히 이해한 설계입니다.

**What doesn't:**
- 전체적으로 데이터 밀도가 높아질 때 시각적 피로도가 증가할 수 있습니다. 정보의 위계(Hierarchy)를 색상(시안/그린/앰버/레드)과 타이포그래피 웨이트로 엄격하게 통제해야 합니다.

---

## Recommended Direction

**Industrial / Utilitarian (기능주의적 산업 디자인)**

이 대시보드는 "비행기 조종석의 계기판"이나 "서버 모니터링 터미널"과 같은 느낌을 주어야 합니다. 
- **불필요한 애니메이션 배제**: 상태 변화는 즉각적이고 명확해야 합니다.
- **데이터 밀도 최적화**: 여백보다는 그리드와 테두리(border)를 활용한 명확한 구획 나누기를 선호합니다.
- **정보의 신호 대비**: 평상시(정상 상태)는 시각적으로 차분하게(muted) 유지하고, 에러나 병목(Rate Limit 등) 발생 시 앰버/레드 색상으로 강렬한 시각적 대비를 주어야 합니다.

## 제안된 기능 평가 및 추천

### 1. 이상 시 자동 확장 (Auto-expand on error)
**[강력 추천]** - **우선순위: 1 (최상)**

- **이유**: 모니터링 툴의 핵심은 "무엇이 잘못되었는가"를 가장 빠르게 보여주는 것입니다. 개발자가 에러를 찾기 위해 트리를 파고드는(drill-down) 수고를 없애줍니다. UX 관점에서 가장 ROI가 높은 기능입니다.
- **구현 조언**: 레이아웃 시프트가 발생하지만, 에러 상황이므로 사용자의 시선을 끄는 긍정적인 효과로 작용합니다. 에러 노드에 펄스(pulse) 애니메이션이나 붉은색 보더 하이라이트를 주어 즉각적인 인지를 돕는 것이 좋습니다.

```css
/* Animation for newly auto-expanded error nodes */
@keyframes errorPulse {
  0% { box-shadow: 0 0 0 0 rgba(239, 68, 68, 0.4); }
  70% { box-shadow: 0 0 0 4px rgba(239, 68, 68, 0); }
  100% { box-shadow: 0 0 0 0 rgba(239, 68, 68, 0); }
}

.tree-node--error.auto-expanded {
  border-left: 3px solid var(--color-red);
  animation: errorPulse 2s ease-out;
}
```

### 2. p95 latency 통계
**[추가 추천]** - **우선순위: 2 (상)**

- **이유**: LLM 기반 앱에서 지연 시간(Latency)은 핵심 품질 지표입니다. 평균(p50)보다 p95/p99 지연 시간이 사용자(또는 대기 중인 개발자)의 실제 답답함을 대변합니다. 제공자/모델별 성능 병목을 파악하는 데 필수적입니다.
- **구현 조언**: 별도의 거대한 패널을 만들기보다는 기존 **Stats** 영역을 확장하거나 마우스 호버(Tooltip) 시 노출되도록 하여 기본 화면의 복잡도를 낮추십시오.

### 3. Cache Saved ms (캐시로 절약된 시간)
**[추가 추천 (마이크로 카피로 통합)]** - **우선순위: 3 (중)**

- **이유**: 시스템의 효율성을 증명하는 기분 좋은(Feel-good) 지표입니다. 개발자에게 시스템이 얼마나 영리하게 동작하고 있는지 피드백을 줍니다.
- **구현 조언**: 새로운 UI 블록을 할당하기에는 중요도가 떨어집니다. 기존 Stats의 "Cache Hit" 항목 옆에 괄호나 작은 텍스트로 붙이는 것을 추천합니다.
- *예시: Cache Hit: 42 (Saved ~45.2s)*

### 4. 타임라인 / Gantt 뷰
**[조건부 추천 (단순화 필수)]** - **우선순위: 4 (하)**

- **이유**: `design_with_experts`나 `ensemble` 워크플로우처럼 여러 전문가가 병렬로 실행되거나 폴백(Fallback) 체인이 발생하는 것을 시각화하기에 가장 좋은 방법입니다. 하지만 구현 복잡도가 매우 높고 화면 공간을 과도하게 차지할 위험이 있습니다.
- **구현 조언**: 거창한 수영레인(Swimlane)보다는 **Call History (TREE)** 모드 내에서 각 노드의 백그라운드에 미세한 프로그레스 바(또는 타임라인 바)를 깔아주는 형태의 **Sparkline 스타일 간트 뷰**를 추천합니다.

```css
/* Inline Timeline Bar Example */
.tree-node {
  position: relative;
  /* ... existing styles */
}

.tree-node::before {
  content: '';
  position: absolute;
  top: 0; bottom: 0;
  /* Calculate based on (start - workflowStart) / workflowTotalDuration */
  left: var(--relative-start-percent); 
  /* Calculate based on duration / workflowTotalDuration */
  width: var(--relative-duration-percent);
  background-color: rgba(var(--color-cyan-rgb), 0.1);
  z-index: 0;
}
```

## Accessibility Notes (A11y)
- **Color Contrast**: 다크 테마에서 시안(Cyan)과 그린(Green)은 텍스트로 사용할 때 배경과의 대비(Contrast Ratio)가 4.5:1을 넘기기 어려울 수 있습니다. 순수 시안(#00FFFF)보다는 약간 톤 다운되거나 명도가 조절된 색상을 사용하여 접근성을 확보해야 합니다.
- **상태의 이중 인지**: 상태(성공, 지연, 에러)를 색상(초록/노란/빨간)으로만 구분하지 마십시오. 색맹 사용자를 위해 아이콘(체크, 경고, 엑스)이나 텍스트 라벨을 반드시 병행해야 합니다. (예: `[OK]`, `[WARN]`, `[ERR]`)
