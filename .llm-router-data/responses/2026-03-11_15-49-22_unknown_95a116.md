### 최종 정리

### 1. 최종 결론

React 상태 관리는 '단일 도구 표준화'가 아닌 **'상태의 성격과 데이터 소유권에 따른 엄격한 계층 분리'**가 최적의 전략으로 합의되었습니다. 

가장 안전하고 실용적인 기본 방향은 **① 로컬 상태 우선 배치를 원칙으로 하고**, **② 비동기 서버 데이터는 서버 상태 전용 도구(React Query 등)로 완전히 격리하며**, **③ 클라이언트 전역 스토어는 다수 화면에서 빈번한 업데이트와 공유가 발생할 때만 제한적으로 도입**하는 것입니다. 

### 2. 가장 설득력 있었던 관점과 이유

이번 토론에서는 실용주의 아키텍트의 **"명확한 상태 승격 기준(Local → Context → 경량 스토어 → RTK)"**과 리스크 중심 검토자의 **"경량 스토어(Zustand)의 유연성이 낳는 리스크 통제 방안"**이 결합된 지점이 가장 설득력 높고 결정적인 통찰을 제공했습니다.

단순히 "복잡해지면 전역 스토어를 도입하자"는 실용적 태도는 자칫 로컬 상태마저 전역 스토어에 집중되는 '쓰레기통화(Garbage-bin anti-pattern)'를 부를 수 있다는 리스크 관점의 지적이 매우 타당했습니다. 이를 방어하기 위해 리스크 검토자가 제안한 엄격한 아키텍처 규칙(액션 기반 쓰기 강제, 구독 범위 제한)을 실용주의 아키텍트가 수용하면서, 가벼운 도구를 쓰되 시스템적 규율을 더하는 가장 안정적인 실무 지침이 완성되었습니다.

### 3. 남은 쟁점과 조건부 판단

대원칙은 수렴했으나, 조직 규모와 프로젝트 특성에 따라 다음 두 가지는 조건부 판단이 필요합니다.

*   **Zustand vs Redux Toolkit(RTK) 선택 분기:**
    *   **Zustand 선택 조건:** 소규모 제품팀, 상태 전이가 비교적 직관적이며 빠른 기능 개발이 우선인 경우. 단, 팀 내부적으로 상태 변경에 대한 코드 리뷰와 컨벤션 통제가 가능해야 합니다.
    *   **RTK 선택 조건:** 다수의 개발자가 동일한 도메인을 병렬로 작업하는 환경, 금융이나 복잡한 폼 위자드처럼 상태 변경 이력(Audit Trail)과 시간 여행 디버깅이 필수적인 경우, 그리고 개인의 역량이 아닌 '시스템'으로 엄격한 단방향 데이터 흐름을 강제해야 하는 경우에 정당화됩니다.
*   **최소 운영 규칙의 강제 수단:** Zustand와 같은 경량 스토어를 도입할 때 룰(직접 수정 금지, 액션 사용 등)을 단순 팀 내 컨벤션에 맡길 것인지, 아니면 Lint 룰이나 Custom Hook 래핑을 통해 시스템적으로 차단할 것인지 팀 차원의 결정이 남아있습니다.

### 4. 실행 가능한 권고

조직 내 아키텍처 가이드라인으로 즉시 적용해야 할 Action Item은 다음과 같습니다.

1.  **데이터 소유권에 따른 서버 상태 격리**
    *   데이터의 진실의 원천(Source of Truth)이 백엔드에 있는 상태는 절대 클라이언트 전역 스토어에 담지 마십시오. 무효화, 재요청 로직은 React Query, SWR 등 서버 상태 전용 도구에 전담시켜야 합니다.
2.  **Context API의 허용 범위 축소**
    *   테마, 다국어(로케일), 세션 유무, 피처 플래그 등 **'읽기 중심이며 업데이트 빈도가 극히 낮은 앱 셸(App Shell) 수준의 공통값'**에만 Context API를 사용하십시오. 빈번한 업데이트가 일어나는 상태에 사용하면 렌더링 병목이 발생합니다.
3.  **명확한 클라이언트 상태 승격 트리거 문서화**
    *   단순히 컴포넌트 깊이(Prop Drilling)가 깊어졌다는 이유로 전역 스토어를 도입하지 마십시오. **'상태 업데이트의 빈도'**가 높고, 독립된 여러 화면에서 **'특정 상태의 파편(slice)만 구독하여 렌더링을 최적화해야 할 때'**를 전역 스토어 도입 조건으로 명문화하십시오.
4.  **경량 스토어(Zustand 등) 4대 필수 방어 규칙 적용**
    *   가벼운 스토어를 채택할 경우 다음 규칙을 팀 표준으로 강제하십시오.
        *   **도메인 분리:** 스토어를 도메인별로 쪼개고 순환 참조를 막을 것.
        *   **단방향 쓰기 강제:** 컴포넌트 내에서 상태를 직접 수정(Mutation)하는 것을 엄격히 금지하고, 반드시 스토어 내부의 Action 함수를 통해서만 상태를 변경할 것.
        *   **구독 최적화:** 성능 저하를 막기 위해 전체 스토어가 아닌 Selector 기반으로 필요한 상태만 구독할 것.
        *   **서버 데이터 캐싱 금지:** 클라이언트 UI/워크플로 상태만 관리할 것.
