# 전문가 추천 기반 추가 질의 오케스트레이션 구현 계획

1차 전문가 응답에서 다른 전문가 의견이 필요하다고 제안하면, 오케스트레이터가 그 제안을 해석해 사용자 승인 기반 또는 제한적 자동 실행 방식으로 추가 질의를 수행하는 기능의 구현 계획이다.

---

## 1. 목표

현재 구조는 전문가 또는 agent를 한 번 호출하고 응답을 반환하는 단발 실행에 가깝다. 이번 기능의 목표는 1차 전문가가 자신의 답변 안에서 "이 부분은 특정 전문가 의견이 있으면 더 좋다"고 제안할 수 있게 하고, 실제 호출 결정은 항상 오케스트레이터가 담당하도록 만드는 것이다.

핵심 목표는 다음과 같다.

- 1차 전문가만 추가 질의를 추천할 수 있어야 한다.
- 오케스트레이터가 추천 내용을 파싱하고 실제 호출 여부를 결정해야 한다.
- 추가 질의는 사용자 승인 방식과 자동 실행 방식을 모두 지원할 수 있어야 한다.
- 추가 질의로 호출된 2차 전문가는 더 이상 다른 전문가를 추천할 수 없어야 한다.
- 무한 루프, 자기 재귀, 비용 폭증, 불필요한 연쇄 질의를 구조적으로 차단해야 한다.

---

## 2. 비목표

이번 범위에 포함하지 않는 것은 다음과 같다.

- 전문가가 직접 다른 전문가를 tool로 호출하는 재귀형 실행 런타임
- 깊이 2 이상 멀티홉 위임
- 전문가 간 병렬 토론 엔진 일반화
- 기존 fallback 체인 전면 재설계
- 모든 tool에 동일 정책을 일괄 적용하는 전역 오케스트레이터 개편

즉 이번 기능은 "1회 제한 추가 질의"에만 집중한다.

---

## 3. 기본 설계 원칙

이 기능은 전문가에게 실행 권한을 주는 것이 아니라, 전문가에게 추천 권한만 주는 방식으로 설계한다.

원칙은 다음과 같다.

1. 추천과 실행을 분리한다.
2. 추천은 1차 전문가만 가능하다.
3. 2차 전문가는 전문가 리스트를 전달받지 않는다.
4. 2차 전문가는 추가 추천을 할 수 없다.
5. 동일 요청에서 추가 질의는 최대 1회만 허용한다.
6. 오케스트레이터는 모든 추가 질의에 대해 호출 깊이, 호출 대상, 호출 사유, 실행 여부를 기록한다.

이 구조를 따르면 연쇄 질의가 아니라 "제한된 보조 의견 확보"에 가깝게 동작한다.

---

## 4. UX 모드

### 4.1 승인 기반 모드

가장 안전한 기본 모드다.

흐름은 다음과 같다.

1. 사용자가 전문가에게 작업을 요청한다.
2. 1차 전문가가 본문 응답과 함께 추가 질의 추천을 남긴다.
3. 오케스트레이터가 이를 감지한다.
4. 사용자에게 "17번 보안 전문가에게 이 쟁점을 추가 질의할까요?"처럼 묻는다.
5. 사용자가 동의하면 추가 질의를 실행한다.
6. 최종 응답에 1차 의견과 2차 의견을 함께 정리한다.

장점은 투명성과 비용 통제가 쉽다는 점이다. 단점은 대화 턴이 늘어난다.

### 4.2 제한적 자동 실행 모드

사용자 편의성 중심 모드다.

흐름은 다음과 같다.

1. 1차 전문가가 추가 질의를 추천한다.
2. 오케스트레이터가 정책 검증을 수행한다.
3. 조건을 만족하면 자동으로 2차 전문가를 한 번만 호출한다.
4. 최종 응답에 "추가로 17번 보안 전문가 의견을 자동 확인함"을 명시한다.

이 모드는 아래 조건이 모두 충족될 때만 허용한다.

- 추가 질의 허용 설정이 켜져 있을 것
- 위임 깊이가 0일 것
- 추천 전문가가 유효할 것
- 동일 요청 내에서 아직 호출하지 않은 전문가일 것
- 2차 호출에 전문가 리스트를 전달하지 않을 것

---

## 5. 응답 포맷 설계

핵심은 추천을 자연어 암시로 두지 말고 구조화된 신호로 받는 것이다. 그렇지 않으면 오케스트레이터가 오탐지하거나, 일반 설명 문장을 추천으로 오인할 수 있다.

권장 포맷은 다음과 같다.

```md
## Main Answer
...

## Follow-Up Recommendation
- recommended_expert: security
- reason: 인증 경계와 입력 검증은 보안 전문 검토가 더 적합함
- suggested_question: 이 설계에서 권한 상승이나 입력 검증 누락 위험이 있는지 검토해줘
- confidence: medium
```

또는 기계 파싱이 더 쉬운 fenced block을 사용할 수 있다.

```json
{
  "follow_up": {
    "recommended_expert": "security",
    "reason": "인증/인가 경계 검토 필요",
    "suggested_question": "이 설계의 보안 취약점 가능성을 검토해줘",
    "confidence": "medium"
  }
}
```

초기 구현은 가장 단순한 구조화 블록 한 종류만 허용하는 것이 좋다.

---

## 6. 오케스트레이터 처리 흐름

### 6.1 1차 전문가 호출

1차 전문가 호출 시에만 전문가 목록과 추천 규칙을 함께 전달한다.

프롬프트에는 아래 정책이 포함되어야 한다.

- 필요한 경우에만 다른 전문가 의견을 추천할 수 있음
- 실제 호출은 네가 하지 않음
- 추천은 최대 1개만 허용
- 추천은 반드시 구조화된 포맷으로 반환
- 충분히 답변 가능한 경우 추천하지 않음

### 6.2 추천 파싱

오케스트레이터는 1차 응답에서 추천 블록을 파싱한다.

파싱 결과가 유효하면 다음을 검증한다.

- 추천 대상 expert가 존재하는가
- 현재 요청의 delegation depth가 0인가
- 추천 대상이 이미 호출된 expert가 아닌가
- 추천 대상이 자기 자신이 아닌가
- suggested_question이 비어 있지 않은가

하나라도 실패하면 추천은 무시하고 1차 응답만 반환한다.

### 6.3 추가 질의 실행

추가 질의 실행 시에는 다음 정책을 강제한다.

- 전문가 리스트를 전달하지 않음
- 추천 기능 사용 금지 규칙을 프롬프트에 명시
- delegation depth를 1로 설정
- 호출 이력에 source expert와 target expert를 기록

2차 전문가 응답은 그대로 반환하지 않고, 오케스트레이터가 1차 응답과 함께 묶어서 사용자용 결과로 정리한다.

---

## 7. 무한 루프 및 연쇄 질의 방지 장치

이번 기능의 핵심은 추천보다 방지 장치다.

반드시 필요한 제약은 다음과 같다.

### 7.1 깊이 제한

- delegation depth 기본값은 0
- 2차 질의가 실행되면 depth를 1로 올림
- depth가 1 이상이면 추가 추천 파싱 자체를 비활성화

### 7.2 재호출 금지

- 이미 호출한 expert는 동일 요청에서 다시 호출 불가
- 자기 자신 추천 금지
- A -> B 이후 B -> A 형태 금지

### 7.3 추천 권한 분리

- 1차 전문가에게만 전문가 목록 전달
- 2차 전문가에게는 전문가 목록 미전달
- 2차 전문가 프롬프트에는 "다른 전문가 추천 금지"를 명시

### 7.4 실행 예산 제한

- 자동 추가 질의는 최대 1회
- 필요하면 시간 제한, 토큰 제한, 비용 제한 추가

## 8. 적용 후보 위치

현재 코드 구조 기준으로 가장 유력한 적용 위치는 다음과 같다.

### 8.1 `src/services/expert-router.ts`

전문가 호출을 감싸는 핵심 계층이다. follow-up metadata와 실행 정책을 추가하기 좋은 위치다.

### 8.2 `src/tools/consult-expert.ts`

사용자가 단일 전문가를 직접 호출하는 흐름에 승인형 또는 자동형 추가 질의를 붙이기 좋은 시작점이다.

### 8.3 `src/tools/review-code.ts`

코드 리뷰 결과 중 특정 파트를 보안, 성능, 데이터 전문가에게 추가 확인시키는 UX에 특히 잘 맞는다.

### 8.4 `src/tools/orchestrate-task.ts`

가장 자연스러운 장기 적용 지점이다. 다만 초기 구현은 범위가 커질 수 있으므로 1차 대상은 `consult_expert` 또는 `review_code`가 더 안전하다.

### 8.5 `src/prompts/experts/*.prompt.ts`

1차 전문가용 추천 규칙 텍스트와 2차 전문가용 추천 금지 규칙 텍스트를 분리해 관리해야 한다.

## 9. 단계별 구현 계획

### Phase 1 - 추천 포맷 정의

목표는 1차 전문가가 구조화된 추천을 반환할 수 있게 만드는 것이다.

작업 항목:

- 추천 블록 스키마 정의
- 1차 전문가 프롬프트 규칙 추가
- 2차 전문가 프롬프트 규칙 초안 작성

완료 기준:

- 특정 전문가가 구조화된 추천을 안정적으로 반환함
- 추천이 없어도 기존 응답 형식이 깨지지 않음

### Phase 2 - 추천 파서 추가

목표는 응답에서 추천 블록을 안전하게 추출하는 것이다.

작업 항목:

- recommendation parser 구현
- 유효성 검증 추가
- invalid recommendation 무시 정책 추가

완료 기준:

- 정상 추천은 파싱됨
- 잘못된 추천은 무시됨
- 일반 텍스트는 추천으로 오인하지 않음

### Phase 3 - 승인 기반 모드 구현

목표는 가장 안전한 UX를 먼저 구현하는 것이다.

작업 항목:

- 추천 발견 시 사용자 확인 메시지 생성
- 승인 시에만 follow-up expert 호출
- 최종 응답 조합 포맷 구현

완료 기준:

- 사용자가 동의할 때만 2차 질의가 실행됨
- 최종 응답에 추가 질의 여부가 명확히 드러남

### Phase 4 - 자동 실행 모드 구현

목표는 제한된 자동 보조 질의를 지원하는 것이다.

작업 항목:

- auto-follow-up 설정 추가
- depth/중복/전문가 재호출 차단 로직 추가
- 2차 프롬프트에서 추천 금지 강제

완료 기준:

- 조건 충족 시에만 자동 추가 질의 1회 실행
- 2차 응답에서 더 이상의 추천이 발생하지 않음

### Phase 5 - 로깅 및 관찰성

목표는 나중에 디버깅 가능한 흔적을 남기는 것이다.

작업 항목:

- source expert, target expert, reason 기록
- auto/approval mode 여부 기록
- skipped reason 기록

완료 기준:

- follow-up 실행/무시 사유를 추적 가능함

## 10. 추천 모드 기본값 제안

초기 릴리스 기본값은 승인 기반 모드가 가장 안전하다. 다만 장기적으로는 자동 모드가 사용자 편의성이 더 좋다.

따라서 권장 순서는 다음과 같다.

1. Phase 1-3까지 구현해 승인 기반 모드 먼저 배포
2. 충분한 로그와 사용 패턴 확인 후 자동 모드 추가
3. 자동 모드는 설정 또는 per-request 옵션으로 활성화

추후 자동 모드가 안정화되면, 기본값을 자동 모드로 바꾸는 것도 가능하다.

---

## 11. 테스트 시나리오

반드시 검증해야 하는 시나리오는 다음과 같다.

1. 1차 전문가가 유효한 추천을 반환하고, 사용자 동의 후 2차 질의가 실행된다.
2. 1차 전문가가 추천했지만 사용자가 거절하면 2차 질의 없이 종료된다.
3. 자동 모드에서 유효한 추천이 있으면 2차 질의가 자동 실행된다.
4. 2차 전문가 응답에 추천 블록이 있어도 무시된다.
5. 자기 자신 추천은 차단된다.
6. 이미 호출한 전문가 재추천은 차단된다.
7. 존재하지 않는 expert 추천은 무시된다.
8. 일반 설명 텍스트는 추천으로 오인되지 않는다.
9. 2차 전문가 프롬프트에는 전문가 리스트가 포함되지 않는다.
10. 최종 응답에 "추가 질의 수행 여부"가 명시된다.

---

## 12. 예상 장점

이 기능이 들어가면 다음 이점이 있다.

- 1차 전문가가 자신의 한계를 솔직하게 드러낼 수 있다.
- 사용자는 필요한 경우에만 더 깊은 전문가 의견을 받을 수 있다.
- 전체 시스템은 여전히 중앙 오케스트레이터가 통제한다.
- 멀티 전문가 협업 품질은 높아지면서도 무한 위임 위험은 낮게 유지된다.

특히 코드 리뷰, 보안 검토, 데이터 설계, 아키텍처 검증 같은 영역에서 효과가 크다.

---

## 13. 최종 판단

이번 기능은 "전문가가 다른 전문가를 직접 호출하는 시스템"으로 가면 위험하고 복잡해진다. 반대로 "전문가는 추가 의견을 추천만 하고, 실제 호출은 오케스트레이터가 제어하는 시스템"으로 가면 현재 `llm-router-mcp` 구조와도 잘 맞고 구현 리스크도 낮다.

따라서 최적의 방향은 다음과 같다.

- 1차 전문가에게만 전문가 리스트를 제공한다.
- 1차 전문가만 구조화된 추천을 남길 수 있게 한다.
- 오케스트레이터가 추천을 파싱하고 승인형 또는 제한적 자동형으로 처리한다.
- 2차 전문가에게는 전문가 리스트를 넘기지 않는다.
- 추가 질의는 최대 1회로 제한한다.

이 설계는 사용성, 안정성, 구현 난이도 사이의 균형이 가장 좋다.
